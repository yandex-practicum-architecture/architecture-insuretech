## Задание 6. Настройка Rate Limiting

### Конфигурация Nginx (nginx.conf):

- см. файл [nginx.conf](./nginx.conf)

```
http {
   # Настройка upstream для балансировки нагрузки
   upstream backend_servers {
       server backend1.example.com;
       server backend2.example.com;
       server backend3.example.com;
   }

   # 1. Определение зоны для Rate Limiting (shared memory zone)
   #    - Это общая память, используемая Nginx для хранения информации о rate limiting.
   #    - `my_limit_zone` - имя зоны (произвольное).
   #    - `zone=mylimit:10m` -  Выделяет 10MB памяти для этой зоны. Это определяет, сколько 
   #      информациио различных IP-адресах и количестве запросов от них можно хранить. 
   #      Размер зоны нужно подбирать исходя из ожидаемого количества уникальных IP-адресов.  
   #      10MB обычно достаточно для небольших и средних приложений.  
   #      Важно!  Если zone будет слишком маленькой, Nginx начнет выбрасывать 
   #      ошибки (слишком много соединений), и rate limiting будет работать некорректно.
   #    - `rate=10r/m` - Устанавливает максимальную частоту запросов: 10 запросов в минуту (10 requests/minute).

   limit_req_zone key=$binary_remote_addr zone=mylimit:10m rate=10r/m;

   server {
       listen 80;

       # 2. Настройка Rate Limiting для конкретного location
       location / {
           #    - `limit_req zone=mylimit` -  Включает rate limiting для этой зоны в этом location.
           #    - `burst=20` -  Позволяет клиенту превысить лимит на некоторое количество запросов (в данном случае, до 20 запросов).
           #      Эти запросы ставятся в очередь и обрабатываются с задержкой. Это позволяет избежать резких отказов клиентам, но может привести к небольшой задержке в обработке запросов.
           #    - `nodelay` -  Запрещает задержку для запросов, превышающих лимит.  Вместо этого, Nginx сразу же возвращает ошибку 429 для этих запросов.  
           #      Если `nodelay` не указан, Nginx будет пытаться сгладить трафик, задерживая запросы, что может привести к задержкам, но не к ошибкам.

           limit_req zone=mylimit burst=20 nodelay;

           # 3. Обработка ошибки 429 (Too Many Requests)
           #    - `error_page 429 = @custom_429` -  Определяет, что делать при получении ошибки 429.  
           #      В данном случае, перенаправляет запрос на именованный location `@custom_429`.

           error_page 429 = @custom_429;

           proxy_pass http://backend_servers;

           # Дополнительные настройки проксирования (опционально)
           proxy_set_header Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
       }

       # 4. Кастомная страница ошибки 429 (опционально)
       #    - `@custom_429` -  Именованный location, который обрабатывает ошибки 429.
       #    - `return 429 "Too Many Requests. Please try again later.";` -  Возвращает клиенту ошибку 429 с кастомным сообщением.
       #      Можно также вернуть HTML-страницу или JSON-ответ.

       location @custom_429 {
		   internal;
		   default_type text/html;
           return 429 "<html><body><h1>429 Too Many Requests</h1><p>Слишком много запросов. Пожалуйста, попробуйте позже.</p></body></html>";
       }
   }
}
```

**Разъяснения и комментарии**:  

1. **limit_req_zone**:  
    •   Эта директива определяет зону памяти, в которой Nginx будет хранить информацию о количестве запросов от каждого IP-адреса.  
  
    •   **key=$binary_remote_addr**:  Использует двоичное представление IP-адреса клиента в качестве ключа. Это более эффективно, чем использование текстового IP-адреса.  
  
    •   **zone=mylimit:10m**:  Создает зону памяти с именем `mylimit` и размером 10MB. Размер зоны должен быть достаточным для хранения информации о всех уникальных IP-адресах, которые мы ожидаем увидеть.  
  
    •   **rate=10r/m**:  Устанавливает лимит в 10 запросов в минуту. Можно использовать другие единицы времени, например, `r/s` (запросы в секунду).  

2. **limit_req**:  
    •   Эта директива применяет ограничение скорости запросов к конкретному location.  
    
    •   **zone=mylimit**:  Указывает, какую зону памяти использовать для `rate limiting`.  
    
    •   **burst=20**:  Устанавливает `burst size`. Это количество запросов, которые клиент может сделать "всплеском" сверх установленного лимита. Эти запросы будут поставлены в очередь и обработаны с небольшой задержкой. Это позволяет избежать резких отказов легитимным пользователям, у которых может быть кратковременное увеличение активности.  
    
    •   **nodelay**:  Если включен, то запросы, превышающие лимит (с учетом `burst size`), будут сразу же отклонены с кодом ошибки 429. Если `nodelay` не указан, Nginx будет пытаться сгладить трафик, задерживая запросы, что может привести к задержкам, но не к ошибкам. В данном примере, `nodelay` включен, чтобы сразу же возвращать ошибку 429 при превышении лимита.  

3. **error_page**:  
   •   Эта директива определяет, что делать, когда Nginx возвращает определенную ошибку.  
   •   **error_page 429 = @custom_429**:  Перенаправляет запросы, получившие код ошибки 429, на именованный location `@custom_429`.  

4. **@custom_429**:  
   •   Это именованный `location`, который обрабатывает ошибки 429.  
   •   **return 429 "Too Many Requests. Please try again later."**:  Возвращает клиенту ошибку 429 с кастомным сообщением. Мы можем изменить это сообщение или вернуть HTML-страницу. Вместо `return`, можно использовать `proxy_pass` для перенаправления запроса на другой сервер, который будет обрабатывать ошибки.  

**Как это работает**:  
1.  Когда клиент отправляет запрос, Nginx проверяет, сколько запросов он уже отправил за последнюю минуту.  
2.  Если количество запросов не превышает 10, Nginx пропускает запрос на backend-серверы.  
3.  Если количество запросов превышает 10, но не превышает 30 (`10 + burst=20`), Nginx ставит запрос в очередь и обрабатывает его с задержкой.  
4.  Если количество запросов превышает 30, Nginx сразу же возвращает клиенту ошибку 429.  
5.  Если клиент получает ошибку 429, он может повторить запрос позже.  

**Как проверить работу**:  
1.  Развернуть конфигурацию с Nginx.  
2.  Отправить больше 10 запросов в минуту с одного IP-адреса.  
3.  Убедиться, что Nginx возвращает ошибку 429 для запросов, превышающих лимит.  
4.  Убедиться, что запросы, не превышающие лимит, успешно обрабатываются backend-серверами.  

**Важные замечания**:  

•   **Burst Size**: Необходимо подобрать подходящий размер burst size. Слишком маленький `burst size` может привести к тому, что легитимные пользователи будут получать ошибки 429. Слишком большой burst size может привести к перегрузке backend-серверов.  

•   **Zone Size**: Также следует подобрать подходящий размер зоны памяти. Если зона памяти слишком мала, Nginx не сможет хранить информацию обо всех уникальных IP-адресах, и `rate limiting` не будет работать корректно.  

•   **Error Handling**: Предоставление пользователям понятного сообщения об ошибке 429. Можем указать время, через которое можно повторить запрос.  

•   **Мониторинг**: Можно настроить мониторинг Nginx, чтобы отслеживать количество ошибок 429 и загрузку backend-серверов. Это поможет определить, правильно ли настроен `rate limiting`.  

Этот конфигурационный файл обеспечивает базовый `rate limiting`. Дополнительно можно использовать различные директивы Nginx. Например, настроить разные зоны `rate limiting` для разных location-ов, или сконфигурировать переменные Nginx для динамической настройки `rate limiting` на основе различных факторов (таких как, типа пользователя или заголовка запроса).
